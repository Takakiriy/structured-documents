設定の渡し方

DI における設定の能動性逆転
疎結合のために設定ファイルを特別扱いする問題

設定オブジェクトの渡し方 4 方式を、SmtpClient を題材に比較する。

「クラスが自分で設定ファイルを読み込む方式」「AppConfig をそのまま渡す方式」を順に検討し、Seemann/van Deursen が書いた DI 本の流儀に沿った方式として「エントリポイントで直接 new する方式」と「用途別に括った構成オブジェクト(SmtpConfig)を渡す方式」の 2 つを提示する。その上で、設定の「能動性逆転」と Composition Root 側の負担を踏まえ、Interface Adapter 層では準疎結合方式 (A) を採ることを推奨する。

略語の説明
  • DI (Dependency Injection): 依存性注入。クラスが必要とする依存を外部から渡す設計。
  • DIP (Dependency Inversion Principle): 依存性逆転の原則。上位モジュールが下位モジュールの詳細に依存しないようにする。
  • ISP (Interface Segregation Principle): インターフェース分離の原則。クライアントは使わないメソッド/値への依存を強制されない。
  • OCP (Open/Closed Principle): 開放閉鎖の原則。拡張に対して開いており、修正に対して閉じている。
  • DDD (Domain-Driven Design): ドメイン駆動設計。
  • POCO (Plain Old CLR/Class Object): 振る舞いを持たない単純なデータオブジェクト。

出発点 密結合のサンプル クラスが自分で設定ファイルを読み込む

DI 本「第 2 章 密結合したコードで構築されたアプリケーション」に書かれているサンプルに対応する実装。

前提となる設定ファイル(config.json)はこのような内容で、すべての案で共通とする。

config.json{
    "smtp": {
        "host": "smtp.example.com",
        "port": 587
    },
    "clientName": "OnlineShop"
}

密結合のサンプル はもっとも素朴な実装。SmtpClient が必要なときに自分で config.json を読み込み、接続情報を取り出して使う。外部からは何も渡さない。

import { readFileSync } from "fs";
import nodemailer, { Transporter } from "nodemailer";

class SmtpClient {
    private readonly transporter: Transporter;

    constructor() {
        // 自分で設定ファイルを読み込んで接続情報を取り出す
        const raw = readFileSync("config.json", "utf-8");
        const config = JSON.parse(raw);
        const host = config.smtp.host;
        const port = config.smtp.port;
        const clientName = config.clientName;

        this.transporter = nodemailer.createTransport(
            { host, port, name: clientName }
        );
    }

    send(message: Message) {
        return this.transporter.sendMail(message);
    }
}

// エントリポイントでの呼び出し
const smtpClient = new SmtpClient();

問題点:

  • (1) 設定ファイルへの暗黙的な依存。 SmtpClient のコンストラクターのシグネチャからは、このクラスが config.json という具体的なファイルに依存していることが全く読めない。利用側はこの事実を知らずに使ってしまう。
  • (2) 設定ファイルの形式への直接結合。 JSON ファイルの読み込みや構造(smtp.host、smtp.port)を SmtpClient が直接知っている。環境変数や別形式に変えるたびに SmtpClient 自身を書き換える必要がある。
  • (3) テストが困難。 テストのたびに実ファイル config.json を用意するか、ファイルシステムをモックする必要がある。
  • (4) 再利用できない。 別のアプリでこのクラスを使おうとしても、config.json という同じ名前のファイルがその場所に存在することを前提にしてしまう。
  • (5) エントリポイントの責務が分散する。 設定ファイルを読む場所がアプリ中に散らばり、エントリポイントが構成の流れを把握できなくなる。
  • (6) 型なしアクセス。 JSON.parse の戻り値を直接参照しているため、タイポや欠落が実行時まで分からない。
  • (7) ISP 違反。 JSON.parse の戻り値はアプリ全構成を含むオブジェクトで、SmtpClient は smtp 以外のあらゆる設定にもアクセスできる。実際に使うのは smtp.host、smtp.port、clientName だけ。

改良案 準疎結合方式 (A) AppConfig をそのまま渡す

密結合のサンプル の問題点(設定ファイルへの暗黙的依存、テスト困難など)を解消するため、設定ファイルの構造に型を付けた AppConfig を導入し、エントリポイントで読み込んだものを SmtpClient に渡す。コンストラクターは、クラスが必要とする host, port, clientName を直接受け取り、テスト用とする。

「準疎結合」と呼ぶのは、疎結合の側に寄ろうとしつつ、fromConfig の中だけ AppConfig 型に従うこと(DDD の Conformist 的な選択)を受け入れる、という意味。クラス本体は AppConfig を知らないが、fromConfig の入口に限って AppConfig 全体への依存を受け入れる。

import nodemailer, { Transporter } from "nodemailer";

class SmtpClient {
    private readonly transporter: Transporter;

    // 通常はこちらを使う(エントリポイントから)
    static fromConfig(config: AppConfig): SmtpClient {
        return new SmtpClient(
            config.smtp.host,
            config.smtp.port,
            config.clientName
        );
    }

    // テスト用: host、port、clientName を直接渡せる
    constructor(host: string, port: number, clientName: string) {
        this.transporter = nodemailer.createTransport(
            { host, port, name: clientName }
        );
    }

    send(message: Message) {
        return this.transporter.sendMail(message);
    }
}

// === Composition Root 側 ===

// 設定ファイルの構造に型をつけたもの(Composition Root に属する)
interface AppConfig {
    smtp: { host: string; port: number; };
    db: { connectionString: string; };
    app: { name: string; logLevel: string; };
    clientName: string;
}

// エントリポイントで読み込み・検証
const appConfig: AppConfig = loadAndValidateConfig("config.json");
const smtpClient = SmtpClient.fromConfig(appConfig);

密結合のサンプルから解消されたこと:

  • (1) 設定ファイルへの暗黙的依存が解消。 読み込みは外部(エントリポイント)に移動した。
  • (3) テストが容易になった。 テストでは new SmtpClient(host, port, clientName) で直接組み立てればよく、ファイルシステムは不要。設定値は既存の config.json を参考にできる。
  • (5) エントリポイントの責務が集約される。 構成読み取りはエントリポイントだけで行われる。
  • (6) 型なしアクセスが解消。 loadAndValidateConfig が AppConfig 型として返すので型付きアクセスになり、起動時に不正な構成を早期失敗できる。

残る問題点(密結合のサンプルから引き継ぎ・形を変えて残る):

  • (2) 設定ファイルの構造への結合が SmtpClient にまで届いている。 設定ファイル読み込みは外に出たが、fromConfig 内で config.smtp.host という JSON 構造を直接参照しているため、設定ファイルの構造変更(例: smtp セクション名の変更)が SmtpClient.fromConfig の修正を要求する。
  • (4) SmtpClient が AppConfig 型を知っている(再利用できない)。 SMTP クライアントに、アプリ全体の構成型への依存が混入する。再利用しようとすると fromConfig の定義内容を編集することになり、OCP 違反となる。この影響については後述「保守性の高さと頻度」で検討する。
  • (7) ISP 違反が型として顕在化。 fromConfig は AppConfig(アプリ全構成)を要求するので、シグネチャの上で「アプリ全体の構成」への依存が明示される。密結合のサンプルでは JSON.parse の戻り値経由で暗黙に存在していた問題が、ここでは型として表面化する。

SmtpClient を直接組み立てる 疎結合のサンプル (B) エントリポイントで直接 new する

DI 本「第 4 章 依存注入のパターン」リスト 4.4 にある Pure DI のサンプル(new HomeController(new ProductService(...)) のようにネストした new でオブジェクト・グラフを構築する形)に対応する実装。エントリポイントで appConfig から値を取り出して直接 new SmtpClient(...) を呼ぶ。

import nodemailer, { Transporter } from "nodemailer";

class SmtpClient {
    private readonly transporter: Transporter;

    constructor(host: string, port: number, clientName: string) {
        this.transporter = nodemailer.createTransport(
            { host, port, name: clientName }
        );
    }

    send(message: Message) {
        return this.transporter.sendMail(message);
    }
}

// === Composition Root 側 ===

// 設定ファイルの構造に型をつけたもの(Composition Root に属する)
interface AppConfig {
    smtp: { host: string; port: number; };
    db: { connectionString: string; };
    app: { name: string; logLevel: string; };
    clientName: string;
}

// エントリポイントで AppConfig から値を取り出して直接 new
const appConfig: AppConfig = loadAndValidateConfig("config.json");
const smtpClient = new SmtpClient(
    appConfig.smtp.host,
    appConfig.smtp.port,
    appConfig.clientName
);

準疎結合方式 (A) から解消されたこと:

  • (2) 設定ファイルの構造への結合が SmtpClient から切り離される。 (A) では fromConfig 内で config.smtp.host という JSON 構造を直接参照しているため設定ファイルの構造変更が SmtpClient.fromConfig の修正を要求するが、(B) では SmtpClient はプリミティブのみを受け取り、JSON 構造を知らない。
  • (4) SmtpClient が AppConfig 型を知らない。 (A) では fromConfig(config: AppConfig) により SmtpClient が AppConfig 型に依存するが、(B) では SmtpClient のコンストラクターはプリミティブのみを受け取り、AppConfig 型を知らない。
  • (7) ISP を満たす。 SmtpClient のコンストラクターは host、port、clientName のみを受け取り、使わない値への依存を強制されない。必要最小限の依存がコンストラクターの引数から直接読み取れる。

(A) と比べたトレードオフ:

  • (2)' 設定キーの所在を SmtpClient から辿りにくい。 (A) では SmtpClient.fromConfig 内に config.smtp.host という参照があり、SmtpClient のクラス定義から設定キーの所在が直接読める。(B) では SmtpClient のコンストラクターを見ても host: string としか書かれておらず、実際の JSON キーは new SmtpClient(...) の呼び出し箇所(エントリポイント)を逆引きする必要がある。IDE の参照元へのジャンプや grep ではノイズが多くなる。

新たな問題点:

  • (9) コンストラクター引数だけでは SmtpClient が必要とする値の集合を型として表明できない。 引数の並びでしか表現されないため、引数が増えると読みづらくなる。JavaScript には名前付き引数がないため、呼び出し側でどの値がどの引数に対応するかをコメントや変数名で補う必要がある。
  • (10) DIコンテナーと相性が悪い。 プリミティブ(string、number)はDIコンテナーの型キーとして機能しないため、Auto-Wiring が効かない。DIコンテナーを使う場合は手動でファクトリ関数を書く必要があり、DIコンテナーを使うメリットがほとんどなくなる。(A) は AppConfig を型キーとしてDIコンテナーに登録できるので、Pure DI でもDIコンテナーでもどちらでも使えるが、(B) は Pure DI 専用と言える。

Composition Root と SmtpClient の分離 構造的疎結合方式 (C) 用途別に括った構成オブジェクト(SmtpConfig)を渡す

AppConfig(設定ファイル全体に型を付けたもの)はそのままに、SmtpClient 専用の SmtpConfig インターフェースを導入する。SmtpConfig は SmtpClient が必要とする値を表すシンプルな型(POCO)。AppConfig から SmtpConfig を取り出す作業は、Composition Root 側の getSmtpClientConfig 関数に任せ、SmtpClient.fromConfig はエントリポイント本体から直接呼び出す。これにより SmtpClient の構築がエントリポイントから直接見える形になる((A) では fromConfig の内部に隠れている)。

import nodemailer, { Transporter } from "nodemailer";

// SmtpClient が必要とする値を表す型(POCO)
interface SmtpConfig {
    readonly host: string;
    readonly port: number;
    readonly clientName: string;
}

class SmtpClient {
    private readonly transporter: Transporter;

    // 通常はこちらを使う(エントリポイントから)
    static fromConfig(config: SmtpConfig): SmtpClient {
        return new SmtpClient(
            config.host,
            config.port,
            config.clientName
        );
    }

    // テスト用: host、port、clientName を直接渡せる
    constructor(host: string, port: number, clientName: string) {
        this.transporter = nodemailer.createTransport(
            { host, port, name: clientName }
        );
    }

    send(message: Message) {
        return this.transporter.sendMail(message);
    }
}

// === Composition Root 側 ===

// 設定ファイルの構造に型をつけたもの(Composition Root に属する)
interface AppConfig {
    smtp: { host: string; port: number; };
    db: { connectionString: string; };
    app: { name: string; logLevel: string; };
    clientName: string;
}

// AppConfig から SmtpConfig を取り出す
function getSmtpClientConfig(appConfig: AppConfig): SmtpConfig {
    return {
        host: appConfig.smtp.host,
        port: appConfig.smtp.port,
        clientName: appConfig.clientName,
    };
}

// エントリポイント本体: SmtpClient の構築が直接見える
const appConfig: AppConfig = loadAndValidateConfig("config.json");
const smtpClient = SmtpClient.fromConfig(getSmtpClientConfig(appConfig));

疎結合のサンプル (B) から解消されたこと:

  • (9) 「SmtpClient が必要とする値の集合」を型で表明できる。 (B) ではコンストラクター引数の並びでしか表現されないが、(C) では SmtpConfig が「この 3 つが SmtpClient に必要」と明示する。引数が増えても読みやすさが保たれる。
  • (10) DIコンテナーと相性がよい。 (B) ではプリミティブがDIコンテナーの型キーとして機能しないため Auto-Wiring が効かないが、(C) では SmtpConfig を型キーとしてDIコンテナーに登録できるので、Pure DI でもDIコンテナーでもどちらでも使える。

新たな問題点:

  • (11) 中間の型・関数に分けるコードが必要。 SmtpConfig インターフェース、fromConfig、getSmtpClientConfig を別途定義する必要があり、(B) に比べてコード量が増える。
  • (12) Composition Root 側の負担が増える。 各クラスごとに getSmtpClientConfig、getDbConfig、getLoggerConfig のような橋渡し関数を書く必要がある。(A) なら appConfig をそのまま渡すだけで済むが、(C) では「AppConfig のどこを取り出して、どう束ね直すか」を Composition Root が個別に決める。クラスが増えれば、橋渡し関数も増える。

(A) と比べたトレードオフ:

  • (2)' 設定キーの所在を SmtpClient から辿りにくい。 (A) では SmtpClient.fromConfig 内に config.smtp.host という参照があり、SmtpClient のクラス定義から設定キーの所在が直接読める。(C) では SmtpClient.fromConfig を見ても config.host としか書かれておらず、実際の JSON キーは getSmtpClientConfig を逆引きする必要がある。IDE の参照元へのジャンプや grep ではノイズが多くなる。

※ メモ: SmtpConfig を interface として書いている理由について。DI 本では POCO にインターフェースを作るのはコストに見合わないとされているが、これは C# では具象クラスとインターフェースを別々に書く必要があり、その労力に対する評価。TypeScript の interface は構造的型付けによりオブジェクトリテラルで満たせるため、ここでいう「不要な抽象」には当たらず、SmtpConfig を interface として書く方式は DI 本の主旨(振る舞いのない単純なデータを渡す)に沿う。

準疎結合方式 (A) を再評価する

疎結合のサンプル (B) および構造的疎結合方式 (C) から解消されたこと:

  • (10) DIコンテナーと相性がよい。 (B) ではプリミティブがDIコンテナーの型キーとして機能しないため Auto-Wiring が効かないが、(A) では AppConfig を型キーとしてDIコンテナーに登録できるので、Pure DI でもDIコンテナーでもどちらでも使える。
  • (11) 中間の型・関数に分けるコードが不要。 (C) では SmtpConfig インターフェース、fromConfig、getSmtpClientConfig を別途定義する必要があるが、(A) ではこれらが不要でコード量が少ない。
  • (12) Composition Root 側の負担が増えない。 (C) では各クラスごとに橋渡し関数を書く必要があるが、(A) なら appConfig をそのまま渡すだけで済む。クラスが増えても橋渡し関数は増えない。
  • (2)' 設定キーの所在を SmtpClient から辿れる。 (B)(C) では実際の JSON キーをエントリポイントや getSmtpClientConfig を逆引きする必要があるが、(A) では SmtpClient.fromConfig 内に config.smtp.host という参照があり、SmtpClient のクラス定義から設定キーの所在が直接読める。

トレードオフの深掘り

(A)(B)(C) のトレードオフを並べたうえで、結論を導く前に、それぞれの方式を選ぶときに見落とされがちな観点を整理する。これらは「自然に書くとなぜ密結合になるのか」「(B)(C) のコストはどこに現れるのか」という問いに対する答えにもなっており、結論の根拠になっている。

⟳ 設定の「能動性逆転」

DIP(依存性逆転の原則)が「依存の方向を逆転させる」ことで上位モジュールを下位モジュールの詳細から守るのに対し、設定の渡し方には別種の「逆転」が起きている。これを 能動性逆転 と呼んでおく。

自然な方向の例として、エンティティとデータベースの関係がある。エンティティ(User)はデータベースの存在を知らず、リポジトリ(UserRepository)が「エンティティをどう書くか」を 呼び出す側で コーディングする。能動性は使う側(リポジトリ)にあり、使われる側(エンティティ)は受動的でよい。これは自然な方向(使う側 → 使われる側)。

一方、設定の場合は、SmtpClient が「自分には host と port と clientName が必要だ」とスキーマを設計したにもかかわらず、疎結合のサンプル (B) の SmtpClient のコンストラクター/fromConfig は 設定オブジェクトを受け取る側 になっている。スキーマの設計者が、そのスキーマに沿った値を受動的に注入される側に回っている。本来の能動性(自分が必要なものを自分で取りに行く)が、DI のフォーマットに合わせるために受動側に押し込まれている。

密結合のサンプル(クラスが自分で config.json を読む)は、この本来の能動性を素直に表現した形に近い。だから「自然に書くと密結合になる」のは、書き手の不勉強だけが原因ではなく、設定というものの本来の能動性に DI のフォーマットが噛み合っていないことの現れでもある。

  • 密結合のサンプル: 本来の能動性(自分で config.json を読みに行く)が素直に表現されている。
  • 方式 (A): 値の取り出し(config.smtp.host など)は fromConfig 内、つまり SmtpClient 側に保たれる。能動性逆転は起きていない。
  • 方式 (B): スキーマ（型）を持たず、値の取り出しもすべてエントリポイント（Composition Root）側に委ねる。能動性逆転が最大化する。
  • 方式 (C): スキーマの所有権(SmtpConfig)は SmtpClient 側に残るが、値の取り出し(getSmtpClientConfig)は Composition Root に移る。能動性が分裂する。

⚖ Composition Root の責務

「自然に書く」と、両端ともに 自分側の責務を少なくしたい引力を感じる。SmtpClient 側は「必要なものは自分のクラス内で完結させたい」、Composition Root 側は「各クラスが自分のことは自分でやってほしい」。つまり、SmtpClient 側からも、Composition Root 側からも、「密結合に倒したい引力」が働いている。更に、密結合の方が責務の境界が守られており、並列開発によるメリットが大きい。(B)(C) はこの引力に逆らって、両端にコストを払わせる方式になっている。

  • Composition Root 側のコスト: SmtpClient に関する設定値の意味を理解した上で、橋渡し関数(getSmtpClientConfig、getDbConfig、…)を各クラスごとに書く必要がある。クラスが増えれば線形に増える。
  • SmtpClient 側のコスト: (C) では自分で設計したスキーマ(SmtpConfig 型)を定義し、その内容を Composition Root が把握するためのレビューが発生する。(B) ではスキーマ型こそ不要だが、コンストラクター引数の意味（どの引数がどの設定キーに対応するか）を Composition Root 側が把握する必要がある。
  • (A) では両端のコストが発生しない: Composition Root は appConfig をそのまま渡すだけで済み、SmtpClient は自分のスキーマを外に教える必要もない。並列開発もしやすい。

◷ 保守性の高さと頻度

疎結合であれば常に保守容易性が高いとは限らない。境界を引いて疎にした分のコストは確実に発生するが、その境界が回収するべき将来のイベントは発生するとは限らない。多くの人にとって 設定オブジェクトの中身の更新のほうが、他のアプリケーションへの再利用や設定ファイルの構造の大改変よりも頻繁にある。発生頻度の低いイベントへの備えは、日常の保守作業を遅くしうる。

(C) が (A) に対して持つ本当の利点は、(i) 設定ファイルの構造を大幅に作り替えるときの SmtpClient への波及を避けられること、(ii) 型シグネチャに「必要な値の集合」を表明できる可読性、の二つ。だが、

  • (i) 設定ファイルの構造の大幅な作り替えは頻度が低い。 構造そのものを根本から作り替えるレベルのイベントは、Interface Adapter 層のクラスに対してそこまで備える必要は薄い。
  • (ii) 可読性の差も小さい。 (A) でも fromConfig の本体に config.smtp.host などと書いてあり、必要な値は読める。素のコンストラクター (host, port, clientName) は (A)(B)(C) で共通。
  • SmtpClient の再利用も (A) で対応できる。 別アプリ用の fromAnotherAppConfig を追加またはそれに置き換えるか、素のコンストラクターを呼べばよい。SmtpClient は Interface Adapter 層のクラスであり、公開ライブラリほどの OCP は要らない。

結論

Interface Adapter 層では準疎結合方式 (A) を採る。 SmtpClient のように、アプリと外部ライブラリ(nodemailer)の間に位置する Interface Adapter 層のクラスでは、fromConfig(config: AppConfig) の形で AppConfig をそのまま受け取ってよい。両端(SmtpClient 側と Composition Root 側)から働く「密結合に倒したい引力」を素直に受け止め、必要になったときに逆引きで直す方が、合計コストが小さい。

汎用ライブラリ層では疎結合のサンプル (B) または構造的疎結合方式 (C) を採る。 公開ライブラリとして外部に出すクラス、複数の Composition Root から組み立てられる部品、設定ファイルの構造そのものが頻繁に作り替わる領域では、両端のコストを払って (B) または (C) を採る価値がある。OCP を強く要求される場面、再利用が常態である場面、ISP を型として表明したい場面では、(B)(C) の利点が実際に効く。

判断の基準は「自然な密結合でも大丈夫か、それとも影響範囲の境界(疎結合)が必要か」を クラスの位置付けに応じて 見極めることに尽きる。(A)(B)(C) は進歩の段階ではなく、層に応じた選択肢として同列に並ぶ。

制約

動的リロードに対応しない。 この方針は起動時に確定した値を渡す前提なので、実行中の構成変更を反映しない。リロード要件がある場合は、変更通知を明示的に扱う仕組み(ファイル監視 + コールバック、Observable など)を別途設計する。
