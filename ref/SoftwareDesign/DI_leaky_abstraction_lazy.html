8.4.2 — LEAKY ABSTRACTION

Lazy<T> による生存戦略の漏洩
—— いつ問題になり、どう畳むか

Lazy<T> を使うこと自体は悪くない。悪いのは「遅延生成」という合成基点の都合を、利用クラスの型に漏らすこと。漏れの目印は利用側に現れる .Value である。

※ 参照したすべてのコードと、コールツリーの対比（YAML）は、この文書のいちばん最後にまとめてある。

前提なぜ Lazy<T> が欲しくなるのか

IUserContext という抽象そのものは、重いとも軽いとも言っていない。遅延が欲しくなるのは、その実装として AspNetUserContextAdapter のような生成コストの高い具象を選んだときだけ。軽い実装を選べば遅延は要らない。

つまり Lazy<T> の要否は実装の選択に従属する話であって、抽象の性質ではない。実装を選ぶのは合成基点（Composition Root）の責務だから、Lazy<T> の知識も合成基点に留めるのが筋になる。

遅延という知識は、実装を選ぶ合成基点に留め、利用クラスには素の IUserContext を渡したい。

漏洩何が「漏れ」なのか

問題は、Lazy<IUserContext> を利用クラスのコンストラクタに直接注入すること。型シグネチャに Lazy<> が出た瞬間、利用クラスは「この依存は遅延生成される」という合成基点の都合を知らされる。利用側は使うたびに .Value で殻を破る必要があり、この .Value こそが漏洩の目印になる。

悪いコードリスト8.18：Lazy<IUserContext> に依存する ProductService を用いた合成基点
// （悪いコード）合成基点側
Lazy<IUserContext> lazyUserContext =
    new Lazy<IUserContext>(                     // ここに書くことは漏洩ではない
        () => new AspNetUserContextAdapter());  // Value が初めて実行されたときだけ実行される

new HomeController(
    new ProductService(
        new SqlProductRepository(new CommerceContext(connectionString)),
        lazyUserContext));    // ProductService に Lazy が漏洩している
悪いコードリスト8.17：漏洩する抽象となる Lazy<T> の利用
public class ProductService : IProductService {
    private readonly IProductRepository repository;
    private readonly Lazy<IUserContext> userContext;

    public ProductService(
            IProductRepository repository,
            Lazy<IUserContext> userContext) {   // 漏洩する抽象（悪い）
        // 遅延の責務を「依存が注入されるクラス」に押し付けている
        // 親（合成基点）から子（外）へ漏洩している
        this.repository = repository;
        this.userContext = userContext;
    }

    public IEnumerable<DiscountedProduct> GetFeaturedProducts() {
        return
            from product in this.repository
                .GetFeaturedProducts()
            select product.ApplyDiscountFor(
                this.userContext.Value);
                // .Value を実行して初めて値が生成され、
                // Lazy が破棄されるまで値は保持され再生成されない。
                // これで遅延生成を実現する。
    }
}

分岐問題が深刻になるのはどんなときか

漏洩が問題になるかどうかは、利用クラスの数でほぼ決まる。

利用クラスが一つだけ

実害は小さい。.Value を呼ぶのも、テストで Lazy<> を組み立てるのも一箇所で済む。組み立てはテスト用ヘルパーを一つ作れば流用できる。

→ 直接依存で十分。プロキシを作る方がかえって手間。

利用クラスが複数・増えうる

同じ抽象を使うクラスが十個あれば、その十個すべてが Lazy<> を受け取り .Value を呼ぶ。.Value の知識がクラス数だけ掛け算で散らばる。

→ ここで問題化。生成戦略の変更が十箇所＋テストに波及する。

評価本が挙げる三つの問題点を吟味する

本の主張吟味判定
テストで毎回 Lazy<> を組み立てる手間が増える テスト用ヘルパーを一つ作れば流用でき、組み立てコストはほぼ消える 弱い
Value が正しいタイミングで呼ばれるか検証するテストが要る 普通に必要な箇所で .Value を読むだけなら遅延は Lazy<T> 自身が保証する。早すぎる呼び出しは「コンストラクタにロジックを入れない」一般原則で防げる。検証が要ってもプロキシ側に移るだけ 弱い
既存依存を Lazy<> に変えるとアプリ全体に波及する 利用クラスが複数あるという前提でのみ成立。.Value の散らばりという本質を突いている 本物

三つのうち実質的に効くのは三番目だけ。テスト関連の論拠は削ると痩せ、プロキシを正当化する理由は「利用クラスが複数あるとき .Value の知識が散らばるのを防ぐ」一点に収束する。

解決仮想プロキシ＝Lazy を IUserContext に変える装置

解決策のプロキシは、結局 Lazy<IUserContext> を IUserContext に変換するアダプタにすぎない。.Value で殻を剥がす作業を一箇所に集約し、利用クラスには IUserContext の顔だけ見せる。一個書けば複数の利用クラスがすべてきれいになる。

良いコードリスト8.19：Lazy<T> を内包する仮想プロキシ（Virtual Proxy）
public class LazyUserContextProxy : IUserContext
{
    private readonly Lazy<IUserContext> userContext;

    public LazyUserContextProxy(Lazy<IUserContext> userContext) {
        this.userContext = userContext;
    }

    public bool IsInRole(Role role) {
        // .Value を使わずに IUserContext.IsInRole を素直に呼ぶ（利用側から見れば）。
        // GetFeaturedProducts に対応する位置のメソッド。
        IUserContext real = this.userContext.Value;  // ここで遅延生成を実現
        return real.IsInRole(role);
    }
}

// リスト8.19 に続く ProductService のコンストラクタ：
public ProductService(
    IProductRepository repository,
    IUserContext userContext)     // Lazy が無いだけの違い
良いコードリスト8.20：仮想プロキシを注入するように変更した合成基点
IUserContext lazyProxy =
    new LazyUserContextProxy(
        new Lazy<IUserContext>(
            () => new AspNetUserContextAdapter()));

new HomeController(
    new ProductService(
        new SqlProductRepository(new CommerceContext(connectionString)),
        lazyProxy));     // Lazy ではなく IUserContext にマッチする値を渡すので良い

プロキシは Lazy を IUserContext に変換するアダプタ。.Value を一箇所に閉じ込める。

代償プロキシは無料ではない

プロキシは IUserContext を実装する以上、そのインターフェイスの全メソッドを実装する義務を負う。メソッドが五つあれば五つすべてを書き、それぞれの中で this.userContext.Value.メソッド名(…) という同じ形の委譲を繰り返す。中身はほぼ同一の定型コード（ボイラープレート）で、インターフェイスにメソッドが増えればプロキシも追従して増える。

軽減策はある

委譲が大変なほどインターフェイスが太いなら、インターフェイス分離の原則の観点で太りすぎを疑う余地がある。小さなインターフェイスならプロキシも小さい。また Castle DynamicProxy のような動的プロキシ生成ライブラリを使えば、定型的な委譲を手書きせずに生成できる。本は教育目的で素朴な手書きプロキシを見せているが、現場ではツールでボイラープレートを消すのが一般的。

前提そもそも「書き換えられない」ことが条件

本文が釘を刺すのは、仮想プロキシが要るのは「開発者が直接手を出せないサードパーティ製のコードを扱う場合」だという点。これは見落とせない。

依存が自前のコードなら、プロキシより先に「実装そのものを直す」

生成コストが問題なら、その具象クラス自身を作り直して生成を軽くしたり、内部で遅延を抱えるよう設計したりできる。つまり Lazy<> という外付けの仕組みに頼る必要がそもそもない。Lazy<> やプロキシを持ち出さざるを得ないのは、対象が外部ライブラリでこちらでは書き換えられないから。書き換え不能なものの生成を外から Lazy<> で包み、その Lazy<> を隠すためにプロキシが要る、という連鎖になる。

結論いつプロキシを使い、いつ使わないか

Lazy<T> の漏洩が本当に問題になるのは、書き換えられない外部ライブラリの重い実装を遅延させたく、かつ同じ抽象を使う利用クラスが複数あって .Value の知識が散らばってしまうケースに絞られる。この条件が揃ったときだけ、全メソッド委譲というプロキシの実装コストを払う価値が出る。

利用クラスが一つなら、合成基点で Lazy<> を組み立てて渡し、利用クラス内で .Value を一回呼ぶ方が安く、プロキシは要らない。依存が自前のコードなら、プロキシより先に実装そのものを直せる。

本がプロキシを推すのは「書き換え不能なライブラリ・複数クラス・将来の変更」という厄介な前提を基準に書いているからで、その前提が当てはまらない場面では、より単純な手段が正解になる。
