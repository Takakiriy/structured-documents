Simple Injector と「自動登録」ページの読み解き

機能の実情 ／ ページの主張 ／ サンプルコード

前提となる事実

この本『Dependency Injection Principles, Practices, and Patterns』の著者の一人 Steven van Deursen は、Simple Injector というDIライブラリの作者本人です。したがって本のコードとライブラリの設計思想は、別々の存在ではなく同一人物による一貫した思想です。

「本に書かれてからライブラリが後追いで対応した」という関係ではなく、もともとSimple Injectorは「規約ベース登録の専用APIをあえて持たず、LINQで書かせる」という哲学のもとに設計されています。

Simple Injector の機能の状況

(1) 一括登録の専用メソッド

container.Register(typeof(IFoo<>), assembly) 系。同じ一つのオープンジェネリックインターフェースを共有する実装群を一度に登録する用途。

各リポジトリが 異なる インターフェースを一つずつ持つ今回のケースは、この想定形に合わないため、このメソッド単体では扱えません。

(2) LINQ + Register ループ

アセンブリをスキャンして規約に合う型を自分で集め、container.Register() を一つずつ呼ぶ方式。

公式ドキュメントが「制約的な専用APIより書きやすく、理解しやすく、柔軟」と明確に推奨している正攻法です。本のサンプルはこちらに該当します。

観点(1) 一括登録専用メソッド(2) LINQ + Register
想定する型の形一つのIFを複数実装が共有各実装が異なるIFを一つ持つ
今回のリポジトリ群合わない合う
条件の決め方ライブラリ既定のパターン開発者がLINQで自由に記述
位置づけ特定用途向けの便利メソッド公式推奨の汎用手法

補足：両方とも内部でアセンブリをスキャンするためリフレクションは使います。「リフレクションを使うかどうか」は両者を分ける軸ではありません。違いは「マッチング条件を誰が決めるか」です。

ページが本当に言いたいこと

著者がライブラリ作者であることを踏まえると、このページは「自社製品の不足の告白」ではなく、普遍的な設計思想の表明です。主張は次の三点に集約されます。

主張その一：規約を見つける思考を身につける

繰り返されるコードに規則性（同じアセンブリにある／名前がRepositoryで終わる／インターフェースを一つだけ実装）を見出し、それを登録の規約として形式化する。この「繰り返しから規約を抽出する思考」が中心テーマです。

主張その二：専用APIは想定が狭いことがある

ライブラリの一括登録メソッドは、想定したパターン（同じIFを共有する型グループ）にしか当てはまりません。万能ではない、という注意喚起です。

主張その三：汎用スキルで解決する

LINQとリフレクションという汎用技術があれば、特定ライブラリのAPIに縛られず柔軟に登録を書ける。他のAPIを個別に覚える必要もなくなる。これはSimple Injectorが掲げる「ベンダーロックインを避ける」という設計原則と一致します。

表面的な記述本当に伝えたいこと
「専用APIでは対応できない」専用APIは想定パターンが狭い。万能と思うな
「LINQとリフレクションで実現する」これが本来推奨される普遍的な方法だ
「他のAPIを学ぶ必要がなくなる」固有APIより汎用知識のほうが価値がある

サンプルコード

本のリスト（規約をLINQで表現し、自作コンテナに登録）

リスト対象アセンブリをスキャンし、名前がRepositoryで終わる実装クラスを抽出して登録

var assembly =
    typeof(SqlProductRepository).Assembly;

var repositoryTypes =
    from type in assembly.GetTypes()
    where !type.Abstract
    where type.Name.EndsWith("Repository")
    select type;

foreach (Type type in repositoryTypes)
{
    container.Register(
        type.GetInterfaces().Single(), type);
}

Service の規約に書き換えた例

応用名前がServiceで終わる実装を、その抽象とともにすべて登録

var assembly = typeof(ProductService).Assembly;

var serviceTypes =
    from type in assembly.GetTypes()
    where !type.Abstract
    where type.Name.EndsWith("Service")
    select type;

foreach (Type type in serviceTypes)
{
    container.Register(type.GetInterfaces().Single(), type);
}

Simple Injector 公式ドキュメントの書き方

公式名前空間で範囲を絞り、各型の各インターフェースに対して登録

var repositoryAssembly = typeof(SqlUserRepository).Assembly;

var registrations =
    from type in repositoryAssembly.GetExportedTypes()
    where type.Namespace.StartsWith("MyComp.MyProd.DAL")
    from service in type.GetInterfaces()
    select new { service, implementation = type };

foreach (var reg in registrations)
{
    container.Register(reg.service, reg.implementation, Lifestyle.Transient);
}

一括登録専用メソッド（想定が合う場合）

専用API一つのオープンジェネリックインターフェースを共有する実装群向け

// IValidator<T> を実装する型をまとめて登録する用途
container.Register(typeof(IValidator<>),
                   typeof(IValidator<>).Assembly);
四つのサンプルのうち、上の三つは構造がほぼ同じです。違いは foreach の中身、つまりコンテナ固有の登録呼び出し部分だけ。これがページの言う「自動登録のコードはどのライブラリでもほぼ共通になる」という指摘の実例です。

「自動登録」か「一括登録」か

本やSimple Injectorが使う「auto-registration（自動登録）」という語は、語感ほど自動ではありません。実態は「一括登録（batch registration）」と呼ぶほうが正確です。

何が自動で、何が自動でないか

この方式が省いているのは、登録文を一つずつ手書きすることだけです。

// これを書かずに済む、という限定的な意味での「自動」
container.Register<IProductRepository, SqlProductRepository>();
container.Register<IOrderRepository,   SqlOrderRepository>();
container.Register<IUserRepository,    SqlUserRepository>();

一方で、登録という行為そのものは起動時に明示的にコードを走らせて行います。各クラスが「自分は登録対象だ」と表明しているわけではなく、スキャンする側が能動的に取りに行く構造です。

Python のデコレーターとの対比

デコレーター（宣言的・静的寄り）

@register のように対象の定義側に印が付く。型を見れば登録されると分かる。結びつきの向きは「対象自身が表明する」。

LINQ 方式（走査的・動的）

登録側が実行時にアセンブリを走査し、条件で拾う。型を見ても登録されるか分からず、規約を知らないと挙動が読めない。

観点Python デコレーターこのLINQ方式
宣言の場所クラス／関数の定義側登録側（外部）が走査
結びつきの向き対象自身が表明収集側が条件で拾う
確定のタイミング定義箇所で明示実行時に走査して確定
規約への依存印の有無で明示的命名やnamespaceという暗黙の規約

用語としての裏づけ

Simple Injector 公式ドキュメントの見出しは Batch-Registration / Auto-Registration となっており、batch（一括）の語を併記しています。実態を踏まえると次のように整理できます。

この方式は、コンパイル時に確定する「静的」でもなく、対象に印が付く「宣言的」でもありません。実行時に GetTypes() でリフレクションし、条件でフィルタしてまとめて登録する処理です。「自動」という語は「手書きの繰り返しを省く」という限定的な意味にすぎず、デコレーターのような定義箇所での静的な宣言とは性質が異なります。実態としては一括登録（batch registration）という呼び方のほうが、何をしているかを正確に表しています。

結論

  • Simple Injector で今回のリポジトリ群が「登録できない」わけではない。一括登録専用メソッドの想定形に合わないだけ。
  • 本のLINQ方式は、Simple Injector と対立する別物ではなく、Simple Injector 公式が推奨する自動登録の正攻法そのもの。
  • 著者＝ライブラリ作者なので、ページは宣伝でも不足の告白でもなく、固有APIへの依存を避け、汎用技術で解決せよという設計思想の表明として読むのが正確。
  • 「自動登録」という語は実態を表しきれていない。デコレーターのような静的・宣言的な仕組みではなく、実行時に走査してまとめて登録する一括登録（batch registration）と呼ぶほうが正確。
